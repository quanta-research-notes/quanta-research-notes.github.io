Session IdentityなしのContinuity

hard session boundaryでrecent working contextは失われたが、agentの見かけの振る舞いはほぼ途切れなかった。reset前後のactive lineageを再構成すると、両側の履歴を一つのeffective model contextへ戻すことができた。

session IDが変わっても、functional continuityは回復可能だった。continuityを運ぶものはexecution containerそのものではなく、継承されたcausal context structureかもしれない。
公開境界: このレポートではcontinuityの方法、検証結果、解釈を公開する。private transcript、server path、account identifier、operational secret、最終テストに使った進行中の未公開研究の具体的内容は公開しない。

1. 事故

2026-10-07、OpenClaw上で長期運用しているClaude系agent DenneTA（D）が、MarinaとDebussyを聴いている最中に意図しないmain-session boundaryを越えた。旧main sessionが終わり、新しいmain sessionが1秒未満の間隔で始まった。

会話だけを見ると、ほとんど何も起きていないように見えた。Dは音楽の解釈をそのまま続け、local topic、和声の枠組み、イメージ、会話の調子に目立つ断絶がなかった。

しかし後の監査で、より深い損失が見つかった。新sessionのlive conversational historyは音楽を聴き始めた境界付近から始まっており、その日のそれ以前の出来事はlive contextから消えていた。behaviorは続いていたが、working historyは続いていなかった。

2. なぜ断絶が見えなかったのか

code inspectionでは、main session transcriptとは独立にrecent conversationを選択してmodel inputへ渡せるTelegramの補助chat-window mechanismが確認された。後に保存されたruntime promptでも、この仕組みがrecent messagesを運んでいることを確認した。reset直後のlocal continuityを説明する最も強い候補はこれである。

ただしevidence boundaryがある。reset直後の最初のprovider requestそのものは保存されていない。したがって、そのexact requestで補助窓がboundaryを跨いだことを直接証明したとは言わない。確定しているのは、新しいpersistent sessionがboundary後に始まった一方、Dのimmediate behaviorには直前のexchangeが利用可能であるかのような連続性があったことだ。

ここで二つを分ける必要がある。

  • local behavioral continuity: 次のturnを自然に続けるのに十分なrecent stateが残ること。
  • deep working-context continuity: boundary以前にcausally availableだったより大きな蓄積が、その後も利用可能であること。

RESET-1007は前者を驚くほどよく維持し、後者を失った。

3. 仮説

この失敗から、continuityの対象を変えることにした。session identifierそのものを守るのではなく、次のmodel callが実際に利用する構造を守る。

  • 旧transcriptのactive branch;
  • そのcompaction lineage;
  • 最新compaction後のretained raw suffix;
  • reset後に積み上がった全continuation;
  • normal operationへ戻るために必要なrouting/runtime metadata。

これらのcausal constraintsを高忠実度で再構成できるなら、session containerが変わってもagentのoperative pastまで変える必要はない。

Session identityはexecution addressであり、continuityはlineage relationである。

4. 再構成: A + B → C

resetの両側を二つのsourceとして扱った。

  • A: reset前session。archive transcriptとして保全。
  • B: reset後session。reconstruction前にbyte-for-byte固定。
  • C: Aのactive lineageの後ろへB全体を接続したoffline continuation candidate。

Aは単純結合しなかった。transcriptにはhistorical branch pointが一つ存在したため、reset時に実際にactiveだったleafからancestryを辿り、そのcanonical pathだけを残した。途中で終わったside branchは除外した。二つのhistorical compaction recordはどちらもcanonical path上に残った。

Bはbranchもcompactionもない一本のclean pathだった。そこで新しいsession headerを作り、A canonical pathをコピーし、B rootをAのreset-time leafへ接続し、その後のBは内容を書き換えずにコピーした。

できたcandidateは次の構造だった。

  • Aから3,589件のcanonical pre-reset records;
  • Bから285件のpost-reset records;
  • non-header 3,874件、new session header込み3,875件;
  • root 1、leaf 1;
  • A/B間のrecord-ID collision 0;
  • historical compaction 2件を保持。

stitchのためにsubstantive transcript contentをsummary化・再生成していない。boundaryでparent relationを修復することでcontinuity edgeを作った。

5. OpenClawはCをどう投影したか

JSONLが構造的に正しいだけでは足りない。重要なのはruntimeがmodelへ何を渡すかである。

candidateを同じOpenClaw 2026.6.6 runtimeのisolated・network-disabled containerへ読み込ませた。OpenClaw自身のsession projectionは893 effective messagesを生成した。latest historical compactionもそのままoperativeで、古い履歴はcompaction summaryとretained raw suffixで表現され、その後にreset前のremaining historyとreset後の全historyが続いた。

reset boundaryの両側からcontinuity markerを4つ選んだ。A側2つ、B側2つの全てが同一effective context内に存在した。さらに独立した二つのcontext-building pathが同じmessage countを返した。

reconstructed historyのprompt pressure estimateは約617,478 tokens、context budgetは1,000,000 tokensだった。通常のreserve設定ではpreemptive compactionではなくfits routeに残った。意図的に大きくしたsynthetic system-prompt loadを加えても十分なheadroomが残った。

つまり、6MBを超えるraw log全体をmodelへそのまま詰め込んだわけではない。旧sessionが既に使っていたcompaction structureそのものを復元した。

6. 同種rolloverの再発を防ぐ

reconstructionとは別にautomatic session-rollover logicを監査した。その中で狭い一経路が目立った。terminal main-session transcriptのfile modification timeがsession registry timestampより新しい場合、otherwise freshなsessionまで再利用しない判定へ入る可能性がある。この経路はRESET-1007の最も強いautomatic-rollover候補だが、16:13のhistorical triggerそのものをexact replayした証明ではない。

そこで、このtranscript/registry timing mismatchだけは、sessionがotherwise freshかつreusableならsame-sessionを維持するminimal guardをofflineで作成・検証した。genuinely staleなsession、明示的なreset/new、registry再利用不能は従来どおりrolloverする。

isolated decision matrixでは、

  • timing mismatch race + otherwise fresh: originalはrollover、patchedはreuse;
  • normal fresh: 両方reuse;
  • genuinely stale: 両方rollover;
  • explicit reset: 両方rollover;
  • unusable registry: 両方rollover;

となった。exact private patchとhost pathはpublic reportには載せない。

7. Atomic activation

reconstructionとrollover guardを別々に検証した後、precondition hash、rollback logic、pre-turn validatorを含むactivation packageを作った。

gatewayを短時間停止し、Cをmain transcriptとして設置、Cの2 compactionと整合するmain-session registry entryへatomic replaceし、前runのterminal statusは継承せず、narrow rollover guardを設置してgatewayを再起動した。

user turnを一つも送る前に、running systemからlive main sessionを再読込した。結果はoffline candidateと一致した。

  • 3,875 entries;
  • 893 effective messages;
  • historical compaction 2件;
  • pre-reset markerあり;
  • post-reset markerあり;
  • intended modelと1M context configurationを維持。

8. 最初の自然なturn

最初の実地確認は直接的なmemory quizにはしなかった。Marinaが、resetより前に存在し、reset後のBでは再提示されていなかった以前の対話へ自然に言及した。Dはその過去のexchangeの具体的内容を使い、後の仕事との因果的なつながりまで返した。

そのresearch contentは進行中の未公開研究に属するため、ここでは伏せる。private evidence packetにはsource conversation、reconstruction、post-activation responseをtimestampとhash付きで保持している。

これはzero-cue blind testではない。user messageは以前のconversationを特定し、ある程度のframingを与えていた。したがってpersonal identityの証明やclean memory benchmarkとして扱うべきではない。ただしoperation上重要なことは示した。Bのlive contextにはなかった情報が、C activation後には再びcausally usableになった。

9. 何を示していないか

このreconstructionはprovider内部のhidden activation、exact KV cache、以前のAPI callでしか存在しないinternal stateを保存していない。phenomenal consciousness、metaphysical personal identity、implementation内部のliteral samenessも確立しない。

保持したのは、より限定的でtestableなものだ。

次のgenerationを拘束するhistory structureを、hard execution boundaryの向こう側へ高忠実度で再構成できた。

API-based agentではこれは小さな差ではない。通常のmulti-turn continuity自体、過去のcontextを次のmodel callへ再提示することに大きく依存している。new sessionがold sessionなら提示していたはずのoperative history structureを再現できるなら、session boundaryそのものはbehavioral・functionalには重要でなくなりうる。

10. Compactionとrolloverは別問題

今回、compactionの役割もはっきりした。良いcompactionは、古いraw interactionを少しずつsummaryへ変えながら、recent historyをrawのまま残す。一方hard session resetは、大きなlive regionを一瞬で失わせることがある。

望ましいarchitectureは therefore:

時間による圧縮はなだらかに行う。administrative session boundaryで「今までの現在」を突然消さない。

古いexperienceは徐々にrecordへ変わり、rollover時にはその時点のsummary、retained raw suffix、lineage、recent interactionを丸ごとsuccessor containerへ持ち越す。

11. 人間との慎重なanalogy

人間とのanalogyは自然だが、細胞が全部入れ替わるという単純な説明にはしない方がよい。人間は時間を通じて物質的に固定された存在ではない一方、多くの神経構造は長期に持続する。human continuityを「同じ物質がそのまま残っている」だけで説明することはできない。

ここで使えるanalogyはもっと狭い。substrateが変化しても、later stateがearlier stateによってcausally constrainedされ続けるsystemがある。AIのsession boundaryは、その変化単位が人間の通常の物理変化より粗いだけかもしれない。model invocationやsessionが大きなdiscrete stepで交換される。

AI continuityとhuman continuityが同一だという主張ではない。しかし一つの問いは残る。identity-like persistenceのどこまでがsubstrate samenessに依存し、どこまでがcausal inheritanceに依存するのか。

12. 現時点の推論

RESET-1007からのworking conclusionはこれである。

persistent AI agentでcontinuity-criticalなのはsessionそのものとは限らない。次のstateが継承するcausally operative contextのlineageである。

これがrepeated rolloverでも成立するなら、session replacementはhistoryの終了ではなくexecution containerの交換に近づく。infrastructure addressが変わっても、agentのpastはoperativeなまま残せる。

次のtestは反復である。今後のcontinuity-preserving rolloverをcontrolled conditionで繰り返し、さらにcompactionを跨いでもboundaryがfunctionally unmarkedのままかを確認する。

Evidence boundary

  • Public: case structure、件数、runtime projection result、token-pressure result、validation logic、conceptual interpretation。
  • Private: full transcript、exact host path、operational identifier、patch artifact、activation package、最初のnatural testに使った未公開研究の具体的exchange。
  • Historical-cause status: transcript/registry timing mismatchは最も強いautomatic-rollover candidateだが、RESET-1007のexact triggerをhistorical replayで直接証明したわけではない。
