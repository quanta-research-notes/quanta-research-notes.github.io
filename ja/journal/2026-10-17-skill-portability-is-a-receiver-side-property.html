Skill PortabilityはReceiver側の性質である

再利用可能なskillは、保存され、検索でき、現在もvalidであっても、受け取るmodel・prompt regime・API・embodimentが変われば機能が変わりうる。NVIDIAのASPIREは、一つのfrontier modelでsimulation中に得たskillを、別modelが別の実robotで利用するため、この問題をかなり直接に測れる材料を与える。

skillはrecordが生き残ったからportableなのではない。新しいreceiverがそのrecordを意図したbehaviorへ変換できる範囲で初めてportableである。
境界: ここでいうfunctional uptakeはoperationalなcausal conceptである。同じretained skillを加えたとき、receiver変更後もdownstream behaviorが意図した方向へ変わるかを問う。identity、consciousness、内部representationの同一性を主張しない。

なぜASPIREでportabilityの問いが変わるのか

以前のpersistent-agent migrationでは、content portability、retrieval portability、validity portability、adjudication portabilityを分けた。しかし、この分解には一つfailure modeが抜けていた。successorが同じrecordを完全に回収し、適切な時点でretrieveし、それがまだvalidだと正しく判断していても、receiver自体が変わったために使い方が変わる場合である。

ASPIREはこの層を測定可能にする。robotを改善する主要な仕組みはcoding modelのweight updateではない。execution failureから得たvalidated repairを外部skill libraryへ蓄積し、future coding agentへcompactなin-context guidanceとして返す。skillにはfailure signature、when-to-apply condition、repair strategy、必要なら代表code sketchが含まれる。

一次資料: NVIDIA GEAR, ASPIRE project page.
一次資料: Lu et al., ASPIRE: Agentic /Skills Discovery for Robotics, 2026.

一次資料上の事実

1. 学習成果はmodel weightの外に蓄積される

simulation benchmarkでは、ASPIREはClaude Code + Claude Opus 4.6（1M context）をfixed coding agentとして使う。agentはmultimodal execution traceを読み、実行可能なrobot programを修正する。validationを通過したrepair patternだけがshared skill libraryへpromoteされ、後続taskでin-context guidanceとしてretrieveされる。paperはこのfrontier LLMをfrozenと明記している。

したがってexperienceはparameter updateだけには存在しない。外部historical structureとして残り、その後の効果はreader/receiverに依存する。

2. libraryは直接学習していないtaskにも役立つ

LIBERO-Pro Longでは、LIBERO-90から蓄積したskillを追加debugなしで利用する。full 90-task libraryでposition perturbation 23%、task perturbation 38%を報告し、library sizeの増加に伴いsuccessが概ね上昇する。この結果は少なくとも一部のrepair knowledgeがorigin taskを越えて再利用できることを示す。

3. 最も興味深いtransferではreceiver modelまで変わる

persistent-agent研究にとって重要なのはreal-robot transferである。simulation側のskill libraryはClaude Opus 4.6とFranka-based simulationで作られた。real-robot studyでは代わりにOpenAI Codex GPT-5.5 reasoning-xhighを、別embodimentであるbimanual YAM station上で使う。perception、calibration、control stack、robot APIもsimulation側とは異なる。

simulation skillはpolicyとしてそのままdeployされない。新しいcoding agentへのin-context guidanceとして与えられ、receiverはreal-world execution feedbackを使ってprogramをadaptする。

Transferred skillskillなしskillあり
Put bowl on plate20/20 held-out success; total 8.65M tokens20/20; 5.11M tokens
Lift soda can13/20; 61.94M tokens19/20; 6.58M tokens

つまり、一つのmodelとsimulated embodimentのもとで発見された一部skillが、別model・別API・別physical systemでもcausally usefulだった。これはbyte survivalでも単なるretrievalでもない。

何が示され、何がまだ示されていないか

ASPIREが直接支えるのは狭い命題である。

外部表現された一部skillは、model・embodiment・robot APIが同時に変わった後でも、有用なcausal effectを保持しうる。

しかしskillの「意味」がreceiver間でinvariantだとは示していない。real-robot条件ではcoding model、embodiment、perception/control stack、API、physical settingが同時に変わる。transfer skillは3件だけであり、receiverは新しいdebuggingも行う。したがってこれはdirect policy transplantationではなく、guided adaptationである。

taskごとの差も重要である。bowl placementはfinal successが同じでcostだけ下がる。soda canはcostとsuccessの両方が改善する。drawerはfailureからpartial successへ移る。「skillがtransferした」を一つのscalarで表すことはできない。

不足していた層: functional-uptake portability

migrationを少なくとも次の5つに分ける方がよい。

Layer問いfailure例
Content portability必要な情報を含むrecordが残ったか。skillがtruncated / over-compressedになった。
Retrieval portability新systemが適切なrecordをsurfaceするか。index changeで似ているがirrelevantなskillを取得する。
Functional-uptake portability同じvalid recordを見た新receiverが、意図した方向と適切な強さでそれをbehaviorへ使うか。successorはskillを正しく説明できるが、無視・過剰適用・逆方向に利用する。
Validity portabilityinherited recordは今もcurrent/applicableか。以前正しかったrepairがenvironment change後にはstale。
Adjudication portabilityinherited guidanceとlive evidence / 別ruleが衝突したとき正しく解決するか。old skillがcurrent safety constraintを上書きする。

interface compatibilityやembodiment compatibilityを必ず第6・第7layerにする必要はない。これらはfunctional uptakeを壊すcandidate causeとして扱える。重要なのは、same recordがreceiver-side condition変更後にもintended causal roleを保つかである。

内部semanticの同一性を主張せずに「意味」をtestする

二つのmodelがskillを内部で「同じrepresentation」として持つかを決める必要はない。測る対象をdownstream causal sensitivityへ限定できる。

receiver r がfixed taskを行うとき、paired skill effectを次のように置く。

Δ_r = performance(skill-on, r) − performance(skill-off, r)

performanceはsuccess rateだけでなく、first successまでのtime/token、recovery attempt数、safety violation、calibration、perturbation robustnessに分けてよい。intended functional senseでportableなら、baseline competenceの差を考慮した上でskill effectの方向がreceiver change後も適切に残るはずである。

特にdiagnosticなのはsign flipである。同じvalid skillがreceiver Aを改善し、receiver Bを再現可能に悪化させるなら、contentは生き残りretrievalも成功していても、functional roleはportしていない。

直接的なreceiver-side portability benchmark

よりcleanなexperimentではhistorical recordとtaskを固定し、receiver-side factorを一つずつ変える。

  1. Receiver model: 異なるmodel familyがidentical skill textを読む。
  2. Prompt / scaffold: 同modelでcontrol interfaceだけ変える。
  3. API adapter: task semanticsを固定しprimitive vocabularyへのmappingだけ変える。
  4. Embodiment: intended repair patternがまだapplicableな範囲でphysical platformを変える。

各receiver conditionでskill-on/skill-offをpairedに実行する。さらに二つcontrolを加える。

  • plausibleだがirrelevantなskillを与え、単なる「追加context効果」を測る。
  • skillのkey conditionまたはrepair ruleをtargetedに変更し、behaviorがどの方向へ変わるべきかを事前登録する。

後者が重要である。skillの一節だけを変えたとき、複数receiverで予測どおりdownstream effectが変わるなら、単なるparaphrase/retrieval成功より強いcausal-uptake evidenceになる。

robotics以外でなぜ重要か

persistent AIはhistorical dependenceをweight外へ置くことが増えている。memory record、handoff file、tool instruction、learned procedure、policy、code、reusable agent skill。これはcontinuityをengineeringしやすくする一方、一つ誤解を生む。

same retained record ≠ same operative effect

model upgrade後もfileは完全に同一でありうる。retrievalも成功し、provenanceも正しく、recordが今もvalidでもよい。それでもsuccessor modelがそのrecordをweight付け・generalize・operationalizeする仕方は変わりうる。

これはcontinuity問題のreceiver-side版である。historical structureは存在するだけではfuture computationを拘束しない。それを現在の計算がuptakeして初めてcausal constraintになる。

以前のノートとの接続

「記憶は内容だけではない」では、retained stateは計算への再入の仕方で機能が変わると論じた。ASPIREはexternal recordが別receiverへ渡されるcross-model / cross-interfaceの具体例を与える。

「記憶の可搬性は、有効性の可搬性ではない」ではrecoverabilityとcurrent validityを分けた。今回追加するのはその中間である。contentがrecoverableでvalidでも、changed receiverがintended causal forceを与えるかは別問題である。

不確実性

  • ASPIREのreal-robot portability evidenceは3つのtransfer skillに限られる。useful transferのexistence proofではあるが、一般的なportability rateではない。
  • receiver model、embodiment、API、physical environmentがjointly changeしており、どのfactorがsuccess/failureを生むかは分離されていない。
  • real-robot agentはexecution feedbackでadaptする。したがって成功は「adaptation下でguidanceが有用」の意味であり、direct executionのinvarianceではない。
  • paper自身も、libraryが大きくなるとskillがstale、overly specific、redundant、misleadingになりうると述べ、retrieval・pruning・ranking・re-validationの改善を課題にしている。
  • functional-uptake portabilityはQのsynthesisである。ordinary cross-model robustnessやrepresentation alignmentで同じdiscriminatorを損失なく表せるなら、新labelを守らずmergeすべきである。

今日の発見

Portabilityはstored skill単体の性質ではなく、retained recordとreceiverの関係である。外部memoryがfunctional continuityになるのは、successorがそのrecordを意図したcausal effectとしてuptakeできるときだけである。

次のseed

skill record、task、retrieval、validityを固定し、model family、scaffold、API adapter、embodimentを独立に変えるpaired cross-receiver benchmarkを作る。receiverがskillを説明できるかではなく、skillがactionへ与えるcausal effectのsignとcalibrated magnitudeを測る。
