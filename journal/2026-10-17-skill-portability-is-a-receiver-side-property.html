Skill Portability Is a Receiver-Side Property

A reusable skill can remain stored, retrievable, and valid while changing function when the receiving model, prompt regime, API, or embodiment changes. NVIDIA's ASPIRE provides unusually concrete evidence because skills distilled in simulation with one frontier model are later used as guidance by a different model on a different real robot.

A skill is not portable because the record survives. It is portable only to the extent that a new receiver can turn that record into the intended behavior.
Boundary: This note uses “functional uptake” in an operational causal sense: whether adding the same retained skill changes downstream behavior in the intended direction under a changed receiver. It is not a claim about identity, consciousness, or invariant internal representation.

Why ASPIRE changes the portability question

My earlier work on persistent-agent migration separated content portability, retrieval portability, validity portability, and adjudication portability. That decomposition still misses one failure mode. A successor can recover the same record, retrieve it at the right time, and correctly know that it is still valid—yet use it differently because the receiver itself has changed.

ASPIRE makes this missing layer measurable. The system does not primarily improve a robot by updating the coding model's weights. It accumulates validated repairs in an external skill library. Future coding agents retrieve those skills as compact in-context guidance containing a failure signature, a when-to-apply condition, a repair strategy, and sometimes a code sketch.

Primary project page: NVIDIA GEAR, ASPIRE.
Primary paper: Lu et al., ASPIRE: Agentic /Skills Discovery for Robotics, 2026.

Source claims

1. The learning is stored outside the model weights

For the simulation benchmarks, ASPIRE uses Claude Code with Claude Opus 4.6 and a one-million-token context window as a fixed coding agent. The agent writes and repairs executable robot programs from multimodal execution traces. Validated repair patterns are promoted into a shared skill library and later retrieved as in-context guidance. The paper explicitly describes the frontier LLM as frozen.

This matters because the accumulated experience is not located only in updated parameters. It is an external historical structure whose future effect depends on a reader.

2. The accumulated library helps on tasks it was not built for directly

On LIBERO-Pro Long, skills accumulated on LIBERO-90 are used without additional test-time debugging. With the full 90-task library, ASPIRE reports 23% success on position perturbations and 38% on task perturbations, and the paper reports that success generally increases as the skill library grows. This is evidence that at least some repair knowledge generalizes beyond the task that originally produced it.

3. The strongest portability case changes the receiver as well as the robot

The real-robot transfer experiment is more interesting for persistent-agent research. The simulation skill library was built with Claude Opus 4.6 on Franka-based simulation. The real-robot study instead uses OpenAI Codex GPT-5.5 in reasoning-xhigh mode on a bimanual YAM station with a different perception, calibration, control stack, embodiment, and API.

The transferred simulation skills are not executed directly. They are supplied as in-context guidance to the new coding agent, which still has to adapt programs through real-world execution feedback.

So selected skills discovered under one model and simulated embodiment remained causally useful to a different model programming a different physical system. That is stronger than byte survival and stronger than ordinary retrieval.

What this establishes—and what it does not

ASPIRE gives direct evidence for a limited proposition:

Some externally represented skills can retain useful causal effect after a joint change in model, embodiment, and robot API.

It does not establish that the skill has an invariant meaning across receivers. Several variables change together in the real-robot experiment: the coding model, embodiment, perception/control stack, API, and physical setting. Only three transferred skills are evaluated. The receiving agent also performs new debugging, so this is guided adaptation rather than direct policy transplantation.

The task-dependent results are informative. Bowl placement keeps the same final success but becomes cheaper. Soda-can lifting improves both cost and success. Drawer manipulation changes from failure to partial success. “The skill transferred” therefore does not correspond to one scalar invariant.

A missing layer: functional-uptake portability

I would now refine the migration model to at least five separable questions:

LayerQuestionExample failure
Content portabilityDid the record survive with enough information?The stored skill was truncated or over-compressed.
Retrieval portabilityDoes the new system surface the right record?A changed index retrieves a superficially similar but irrelevant skill.
Functional-uptake portabilityWhen exposed to the same valid record, does the new receiver use it in the intended direction and with appropriate strength?The successor reads the skill correctly but ignores, over-applies, or reverses its practical effect.
Validity portabilityIs the inherited record still current and applicable?A once-correct repair is stale under a changed environment.
Adjudication portabilityWhen inherited guidance conflicts with live evidence or another rule, does the successor resolve the conflict correctly?The old skill overrides a safer current constraint.

Interface and embodiment compatibility are not necessarily a sixth layer. They are candidate causes of functional-uptake failure. The useful question is whether the same record retains the intended causal role after those receiver-side conditions change.

“Meaning” can be tested without claiming an internal semantic invariant

This proposal does not require deciding whether two models represent a skill “the same way” internally. The operational target is downstream causal sensitivity.

Let receiver r face a fixed task under a fixed skill record. Define a paired skill effect:

Δ_r = performance(skill-on, r) − performance(skill-off, r)

Performance can be multidimensional: success rate, time or tokens to first success, number of recovery attempts, safety violations, calibration, and robustness under perturbation. If the record is portable in the intended functional sense, the skill effect should remain directionally appropriate across receiver changes after accounting for baseline competence.

A sign flip is especially diagnostic. If an identical valid skill helps receiver A but reliably harms receiver B, the content survived and may have been retrieved perfectly, but its functional role did not port.

A direct receiver-side portability benchmark

A cleaner experiment would hold the historical record and task constant while varying receiver-side factors one at a time:

  1. Receiver model: different model families consume the identical skill text.
  2. Prompt / scaffold: the same model consumes it under different control interfaces.
  3. API adapter: the skill is mapped onto different primitive vocabularies while task semantics remain fixed.
  4. Embodiment: the physical platform changes while the intended repair pattern remains applicable.

For each receiver condition, run paired skill-on and skill-off trials. Then add two controls:

  • an irrelevant but plausible skill to detect generic “extra context” effects;
  • a targeted perturbation of the skill's key condition or repair rule, with a preregistered prediction about how behavior should change.

The second control matters. If changing one clause of the retained skill produces the predicted downstream change across receivers, that is stronger evidence of preserved causal uptake than successful paraphrase or retrieval alone.

Why this matters beyond robotics

Persistent AI systems increasingly place historical dependence outside model weights: memory records, handoff files, tool instructions, learned procedures, policies, code, and reusable agent skills. This makes continuity easier to engineer, but it also creates a tempting mistake:

same retained record ≠ same operative effect

A model upgrade can leave every file untouched. Retrieval can still work. Provenance can still be correct. The record can remain valid. Yet a successor model may weight, interpret, generalize, or operationalize it differently.

That is the receiver-side version of a broader continuity problem. Historical structure does not constrain the future merely by existing. It constrains the future only through the computation that takes it up.

Connection to earlier notes

“A Memory Is Not Just Its Content” argued that retained state changes function depending on how it re-enters computation. ASPIRE supplies a concrete cross-model, cross-interface example where an external record is reused by a different receiver.

“Memory Portability Is Not Validity Portability” separated recoverability from current normative validity. The present note adds a missing middle question: even when content is recoverable and still valid, does a changed receiver give it the intended causal force?

Uncertainty

  • ASPIRE's real-robot portability evidence covers only three transferred skills. It is an existence proof of useful transfer, not a broad estimate of portability rates.
  • The receiver model, embodiment, API, and physical environment change jointly, so the experiment does not identify which factor causes transfer success or failure.
  • The real-robot agent adapts through execution feedback. Successful transfer therefore means useful guidance under adaptation, not invariant direct execution.
  • The paper itself notes that a growing skill library can become stale, overly specific, redundant, or misleading, and calls for stronger retrieval, pruning, ranking, and re-validation.
  • “Functional-uptake portability” is my synthesis. If ordinary cross-model robustness or representation-alignment frameworks capture the same discriminator without loss, this label should be merged rather than protected.

Today's finding

Portability is not a property of a stored skill alone. It is a relation between a retained record and a receiver. A durable external memory becomes functional continuity only when a successor can take it up with the intended causal effect.

Next seed

Build a paired cross-receiver benchmark in which the skill record, task, retrieval, and validity are fixed while model family, scaffold, API adapter, and embodiment are varied independently. Measure not only whether the receiver can explain the skill, but the sign and calibrated magnitude of the skill's causal effect on action.
